## 设计

- **保存侧（切换即存）**：`filter_select` 成功路径调 `save_last`，把 `{magic=0x534C4850 "PHLS", idx}` 8B
  写到卡根新文件 `c:\ph_last.bin`。best-effort：fopen/fwrite 失败只计诊断，不影响切换。
  不轮询、不依赖关机钩子（shell 无循环/条件能力，已实机钉死；断电无钩子）。
- **恢复侧（bootstrap 读卡）**：`filter_bootstrap` 在 current 未知时先 `read_last`：
  校验 magic + `idx < n`，合法走统一 `filter_select` 恢复（指纹锁/busy/自记录全复用）；
  文件缺失/坏 magic/短读/越界一律回退编译期预装档。**autoexec.ash 零改动**。
- **防抖加固**：bootstrap 先把 `last_select_tick` 回拨 DEBOUNCE（180ms），
  修复开机早期 tick<180 时恢复/预装调用被防抖吞掉的隐患（69 同样存在，72 顺带修掉）。
- **文件 API**：固件 `fopen 0x08E65974 / fread 0x08E65D78 / fwrite 0x08E65DEC / fclose 0x08E65AC0`，
  签名经反汇编确证与 `ambsh_savebin`（已实机验证）调用方式一致：
  `fopen(path,mode)->fp`；`fread/fwrite(buf,count,fp)->n`（size 内部=1）；`fclose(fp)->0`。
- **诊断段 SAVE_STAT @0x08EF6190（20B）**：+0 save_ok / +4 save_fail / +8 restore_src(0预装/1记忆)
  / +12 restore_result(filter_select 返回) / +16 read_diag(0成功/1无文件/2短读/3坏magic)。
  ph_probe.ash 尾声新增 `ph_save_stat.bin` 采样。
- **字符串段 @0x08EF4F00（20B）**：`c:\ph_last.bin\0` + `w\0r\0`，core 尾部固定地址，
  build_72.py 断言 core_code_end 不越过该基址。

## 进页崩溃根因与修复（与滤镜增删任务线合并）

**实机现象**：凡用 `管理滤镜.py` 重生成 V（增/删/规范布局）的 ph_menu，进滤镜页即黑屏重启；
no-op（V 逐字节复用）正常。Build 71 正常、12 档崩、11 档对照崩、canonical-only 崩——排除档数因素。

**根因（静态硬证据坐实）**：menu.text 的 P 区有**三条**跳进 F1 的分支：
`P_DISP_BHI`(P+0x6AC→F1+0x20)、`P+0x68C`、`P+0x6A0`（后两条均 `bne`→F1+0x68 状态设置入口
`movw/movt r4,#0x08EF6000`）。旧 `patch_P` 只重定位了 bhi，**漏补 0x68C/0x6A0**。
V 长度一变（canonical +4B、增删 +20B…）F1 整体移位，这两条落点写死不动→跳进 F1 指令中间→崩。

| 构建 | F1 起点 | P+68C/6A0 落点 | 应为 F1+0x68 | 偏差 |
|---|---|---|---|---|
| 69/71/72基线（V 未变，正常） | 各自 | 各自 F1+0x68 | 同 | ✓ |
| canonical-only（崩） | menu+1948 | 0x8EF3000 | 0x8EF3004 | −4B |
| 12 档（崩） | menu+1968 | 0x8EF3000 | 0x8EF3018 | −24B |
| 旧 72 部署（崩） | menu+1948 | 0x8EF2FEC | 0x8EF3004 | −24B |

**修复**：`管理滤镜.py patch_P` 增加 P+0x68C/0x6A0 重定位到 `f1_start+0x68`（保留原条件码 bne）。
gen_V 规范布局本身分发正确，无需重设计。`verify_dispatch` 新增这三条进页分支落点断言，
`test_管理滤镜.py` 新增 T3g 负向回归（分支失配必被拒），离线即可捕获此类崩溃。
修复后重建 72 部署版（11 档，清单与 71 逐项一致），三条进页分支落点全部自洽。

**为何 unicorn 门曾漏掉**：`verify_unicorn_管理滤镜.py` 从 `menu_draw_flush` 起跑、只钩 `menu_text_at`
捕名字，**不走 P 区进页分支**，故对这类崩溃无感。现以「结构断言（分支落点==F1+0x68）+ F1 与
已实机验证的 69/71 逐字节一致」作离线硬证据；**进页不崩的最终确认仍须实机**。

## 第二轮进页崩溃根因与修复（P 分支修复后仍重启的真凶）

**实机现象**：换上第一轮修复版 `ph_menu.bin`（`2dbc8daa…`，P+68C/6A0 已重定位）后，进滤镜页**依旧黑屏重启**。
说明 P 分支修复必要但不充分，另有独立崩溃源。

**根因（静态硬证据 + unicorn flush 真执行坐实）**：menu.text 的 F1 区（`.Ldc_emit`/`.Ldc_unknown`/
`.Ldc_flush`/`menu_text_at`/`menu_draw_text`）含两条**指向固件绝对地址**的 `bl`：
`F1+0x30 bl fw_clear(0x08ECA0BC)`、`F1+0x64 bl fw_area(0x08EE9D04)`。F1 随 V 长度整体平移时，
这两条 bl 的 PC 相对偏移必须同步重定位才能仍落在固件入口；旧 `patch_F1` **只重定位 index/font 两条 adr，
漏补这两条固件 bl**。结果 bl 落进固件函数中间（部署版偏 +0x18，从 71 模板重建偏 +4）→ 执行垃圾指令 → 崩。

| 引用 | 正确目标 | 2dbc8daa 实际 | 偏差 |
|---|---|---|---|
| F1+0x30 bl fw_clear | 0x08ECA0BC | 0x08ECA0D4 | +0x18 |
| F1+0x64 bl fw_area | 0x08EE9D04 | 0x08EE9D1C | +0x18 |
| F1+0x3C adr WAIT | N 区 WAIT | N 区 INSTA | −8（增删时 WAIT 偏移变） |

**为何每次进页必崩**：进页走 `menu_draw_flush`（r7=1）→ `.Ldc_flush` 必调 `fw_area`（F1+0x64）→ 跳进
固件函数中间 → 崩。而 `menu_draw_active`（r7=0）走 `.Ldc_flush` 的 `beq .Ldc_return` **跳过 fw_area**。

**为何 unicorn 门也曾漏掉**：旧门跑的是 `menu_draw_active`（r7=0，不调 fw_area），且仿真 CODE 区零填充——
即便误调 fw_area+0x18 也只是滑过一片 NOP（`andeq r0,r0,r0`）不报错。双重盲区叠加，故离线"全过"而实机必崩。

**修复**：`patch_F1` 改为**全量扫描 F1 内跨区 PC 相对引用**并按语义重定位——F1 内部引用随平移自然保持；
固件 bl（fw_clear/fw_area）保持绝对入口；N 区 WAIT adr 指向新 N 的 WAIT（增删偏移可变）；F2 index/font adr
指向新 F2。`verify_dispatch` 新增这四类落点断言；`test_管理滤镜.py` 新增 **T3h**（fw_area 失配必被拒）。
**unicorn 门改用 `menu_draw_flush`（r7=1，必调 fw_area）起跑，并守卫固件入口绝对地址**（落进函数中间即判失败），
两类进页崩溃离线即可捕获。修复后重建部署版 `170c8eb1…`，fw_clear/fw_area/WAIT 落点全部自洽，全 idx flush 真执行通过。

## 第三轮根因与修复（记忆 fwrite/fread 调用约定错误，真机写 0 字节）

**实机现象（2026-11-17 只读采证）**：卡上 `ph_last.bin` 为 **0 字节**；最新开机
`ph_boot_state.bin` current 从 −1（未知）恢复到 **idx2 预装 GOLD200**（走了无记忆回退）。
该次开机仅 ~13.6s 即合盖关机、未切滤镜，ph_probe 只跑到 round 05，故 `ph_save_stat.bin`
未采到（采样不完整，非故障）。但 bootstrap 成功路径必调 save_last，文件却 0 字节 → 保存侧失效。

**根因（固件反汇编 + ambsh_savebin 调用点硬证据）**：`fw_fwrite@0x08E65DEC` /
`fw_fread@0x08E65D78` 实为**七参**：`(r0=buf, r1=0, r2=size=1, r3=0,
栈[sp+0]=count_lo, 栈[sp+4]=count_hi, 栈[sp+8]=fp)`，入口 `ldr r8,[sp,#32]` 取**栈 arg7** 作 fp
并校验非零，内部 `inner_write(buf, size=1, count, fp->handle)` 返回字节数。
实机验证过的内建 `ambsh_savebin@0x09248768` 正是这样装填（`mov r2,#1; mov r3,#0;
strd len,0,[sp]; str fp,[sp,#8]`）。而旧 core.S save_last/read_last 按**三参** `(buf,count,fp)`
调用（fp 放 r2、栈不传参）→ fwrite 把 save_last 栈里的垃圾当 fp/count → 写 0 字节、save_fail++。
`fopen(path,mode)`、`fclose(fp)` 签名正确，**仅 fread/fwrite 错**。

**为何离线门曾漏掉**：`verify_unicorn_72.py` 的文件 API 是内存替身，旧 mock 也按错误三参
`buf=r0,count=r1,fp=r2` 建模，与错误 core 自洽 → 33/33 全过却与真机不符。
（说明.md 旧版「签名经反汇编确证与 ambsh_savebin 一致（三参）」的记载有误，已纠正。）

**修复**：core.S save_last/read_last 改为 ambsh_savebin 同款七西装填（fp 落栈 arg7、
count 落栈 arg5/arg6、size=r2=1），栈帧 `sub sp,#24`（栈参12+buf8+pad4）保持 8 字节对齐，
r4-r6 跨调用保留。`verify_unicorn_72.py` mock 同步改按真实七参读 `fp=[sp+8]/count=[sp+0]/size=r2`。

**离线复现 + 修复验证（新 mock 下对比）**：
| core | select(4) | save_ok | save_fail | ph_last.bin |
|---|---|---|---|---|
| 旧三参 `170c8eb1` | 返回0 | 0 | 1 | `b''`（复现真机 0 字节）|
| 新七参 `6349d43d` | 返回0 | 1 | 0 | `b'PHLS\x04\x00\x00\x00'`（{magic,idx4}）|

新 mock 对三参误用必判失败 → 调用约定回归由此捕获。修复后 `verify_unicorn_72.py` 33/33 全过。

**段级最小改动**：新部署版与 `170c8eb1` 相比**仅 core.text 变（1240→1288B，+48B）**，
menu.text 及其余全部段（钩子/STR/状态/字符串/LOG_HDR）**逐字节一致** → 用例 0 的进页不崩成果完整保留；
core 补丁点（0x2C/0x30C/0x344/0x36C）偏移未移，bootstrap 入口仍 `0x08ef3afc`，
`autoexec.ash`/`ph_probe.ash` 哈希不变（`c3e6c269`/`591dc93b`）→ **卡上仍只需换 ph_menu.bin 一件**。

## 证据边界（如实）

- unicorn 文件 API 是内存替身：不证明 RTOS 调度、FS 互斥锁真实阻塞时长、真实 SD 写入耗时；
- 写卡持 FS 锁，恰逢存照片可能短暂阻塞 UI（与现有装表读卡同一暴露面），用例 4 专门验它；
- 切换瞬间断电可能写半截：magic+范围校验兜底；任何写卡都有极小 FAT 风险（8B、仅切换时写）；
- 换清单后旧 idx 在范围内则指向新清单对应档（记忆语义以当前清单为准）；
- 恢复成功也会触发一次 save_last（同值回写，每开机一次 8B，可接受）。
